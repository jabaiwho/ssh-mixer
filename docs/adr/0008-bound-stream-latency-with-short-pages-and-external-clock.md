# Bound stream latency with short pages, external-clock playback, and Stream Epochs

SSH-mixer will encode 10 ms Opus frames, flush one 10 ms Ogg page per frame, and run FFplay with its external monotonic clock as synchronization master. The source cadence is fixed across platforms; Linux, Windows, and Experimental macOS Receiver adapters use the same external-clock playback policy. Receiver Protocol remains v1 because operations and message shapes do not change.

The earlier one-page-per-frame fix removed Ogg's approximately one-second default batching delay, but a long-running Windows Session could still accumulate seconds of playback latency that a stream restart cleared. A real-device Tailscale A/B test with wireless USB audio found no material sender/TCP backlog. With external synchronization, FFplay reported a zero-kilobyte audio queue and master/audio clock difference between -2 ms and +15 ms during a ten-minute diagnostic window. A 10 ms source cadence then remained visually synchronized for more than 110 minutes while the TCP send queue remained negligible. A later Session nevertheless accumulated visible drift after approximately 135 minutes. A subsequent controlled observation found Receiver audio approximately two seconds behind video after 7 hours 54 minutes while the encoder-to-SSH queue was empty, the SSH transmit queue held only 68 bytes, and local audio reported no queued latency. A manual refresh immediately restored synchronization with the same near-empty sender and transport queues. External-clock playback is therefore useful continuous correction but not a sufficient bound by itself; the accumulating state is downstream of the source, local mix, and SSH transport.

An isolated real FFmpeg/FFplay timing harness measured a median near 158 ms with 20 ms frames, near 135 ms with 10 ms frames, and no further improvement with 5 ms frames. We therefore reject 20 ms as avoidable latency and 5 ms as overhead without measured benefit. Ten-millisecond pages add roughly 22 kbit/s of Ogg framing overhead at 100 pages per second; audio coding remains at the selected bitrate.

Each remote stream now runs as a bounded Stream Epoch inside the explicitly started Session. After 15 minutes, SSH-mixer passively waits for at least one second below -50 dBFS and recreates only FFmpeg, SSH, and Receiver playback at the first such silence. If no silence occurs, it forces the same refresh at 30 minutes. Routing, selected sources, privacy lifecycle, active indication, and Session consent remain active; the remote output may have a brief audible gap. The old pipeline terminates before detached replacements start, and neither local launch nor the non-PTY Receiver operation creates a terminal, display, notification, focus change, or overlapping playback pipeline. Process creation and SSH negotiation have a brief unavoidable resource cost. The only sustained addition is an in-process silence scan in the existing encoder; it creates no second pipeline and stores no audio. In a five-run synthetic local benchmark, processing 600 seconds of Opus audio used median CPU times of 5.714 seconds without the filter and 5.870 seconds with it: 0.156 CPU-second extra per 600 seconds of audio, approximately 0.026% of one core when paced in real time. This characterizes the tested machine rather than guaranteeing zero cost on every system. A failed replacement stops visibly and follows normal ownership-safe cleanup rather than silently retrying or falling back.

This revises the earlier rejection of automatic periodic refresh. The observed recurrence showed that continuous clock correction alone did not bound all playback layers, while complete pipeline recreation is empirically known to clear their accumulated state. A future bounded native playback adapter may remove the interruption and provide a stricter latency guarantee, but it requires separate dependency, permission, rollback, protocol, and real-device review.

The deterministic latency check parses real FFmpeg Ogg output and fails if any audio page spans more than one 480-sample frame at 48 kHz. Policy tests cover the 15-minute silence threshold and 30-minute hard deadline. Session tests require replacement of only the remote pipeline, partial-launch cleanup, and visible failure behavior. Receiver adapter tests retain external-clock invocation while existing protocol and forwarding-rejection tests preserve the security boundary.

Protocol-v1 patch compatibility remains intact: plugin 0.1.1 applies bounded Stream Epochs with Receiver 1.1.0 or 1.1.1. Receiver 1.1.0 does not acquire external-clock correction, while the separately approved signed Receiver 1.1.1 update adds that continuous correction within each epoch. Neither compatibility nor the epoch policy silently installs a Receiver update.
